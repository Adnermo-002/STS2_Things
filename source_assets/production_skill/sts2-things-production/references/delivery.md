# 验证、版本与交付

## 当前环境与资料

先查实际游戏、目标 DLL、引用哈希、源码 scope 和项目清单。V107／V111 等目录名可能指旧的、被错误识别的参考文件；不能凭目录名断定它与玩家运行客户端一致。切换 Steam 分支后，目标程序集、依赖和 PCK 要匹配，避免用旧客户端资源冒充新版本验证。

支持版本以当前 manifests、项目和 `docs/UNIFIED_PACKAGE.md` 为准。新接口或 Harmony 目标先对照该目标实际 API；例如 ActModel 的必须覆写接口遗漏会到启动／换章时才暴露。

MCP 和脚本操作路线由 `sts2-workbench` 提供。使用当前配方、参数和检查入口，不在 Skill 中冻结构建目录、模型数量、Steam PID 或某个旧版本号。

## 验证范围服从任务

用户有过“只制作、不要测试”，也有过“全量测试这次更新，不改版本号”。这些是任务范围，不是永久禁止或永久授权启动游戏。

- 明确不测试：完成所需制作与构建／导出（除非用户也排除构建），说明未执行的原生、实机或联机验证；不能暗中运行探针再把它称为普通制作。
- 要求测试：对本轮改变、关键交互和目标版本执行有意义的检查。怪物生命周期、临时牌、死亡、溢出、插入回合、取消、队伍归属、UI 遮挡、存档与章节推进按风险选取。完成相关检查后停止无理由扩展。
- 骨骼与画风需要实际图像／播放自审；静态合法、像素差异、骨数或高断言数量不等于动作好看。
- 对游戏命令读取新状态／截图核实效果。一次“completed”只说明分派结束；用户已经复现的问题要进入修复闭环，不只解释或列建议。
- 使用独立测试身份／存档保护当前玩家进度。同进程多人模型测试不等于多机联机，无防御轨迹不等于胜率，全局禁用补丁后的问题复现也不要误归因到本轮内容。

## 发布产物

按当前工程的统一包流程构建所有支持目标、兼容引导和所需可选桥接。只发布正确的 runtime 文件；编辑原画、工具依赖、凭据和临时截图不进入游戏资源包。Godot 构建后挂载最终 PCK 核对场景、预载资源及本地化，不能只检查源目录存在。

对动态原版枚举的背景目录遵守文本资源合同，注意 `.tscn.remap` 混入导致加载失败。双版本包核对内嵌实现哈希和模型集合，再检查 ZIP CRC 与条目哈希。

正常更新使用明确版本与交付记录。用户说“这次不动版本号”时保留版本，并用哈希／构建记录区分同号包；检测到其他工作落地的构件或同号发布包时先比较来源，保留现有更新与唯一回滚材料，不覆盖共享构建目录碰运气。

安装属于已授权范围时继续完成，但先取得实际游戏关闭状态；不强退用户正在玩的会话。若游戏未退出，准备完整包，明确尚未安装及生效条件。Workbench 安装器可能只复制 manifest／DLL／PCK，**还要核对当前包列出的 BaseLib 等侧载文件**，不能把三文件成功当作整包一致。

工坊推送、改简介或上传预览依用户当次授权执行；只制作／构建不自动推送。获准发布后，保留要求保留的现有标题、描述、标签、预览图或设置，并核查实际远端结果，不只看上传进程退出码。

## 维护源与最终说明

维护源与发布图分开保存：`source_assets` 保留原画、选择版本和补绘；`tools`／`scripts` 保留可重建入口；`build/<任务名>` 存放日志与预览；`docs`／`design` 记录当前决定和历史基线。目录名 `.tmp`、`output` 或“backup”不代表内容可全删，里面可能有唯一原画、源码、依赖或回滚版本。

最终给出实际结果、简短验证及限制、可打开预览／包路径、安装和发布状态。文件与宣称来自同一构件；未运行实机时明确说明，避免将历史检查写成这次已执行。

工具记录与项目维护参考：`docs/WORKSPACE_LAYOUT.md`、`docs/UNIFIED_PACKAGE.md`、`docs/DUAL_VERSION_SUPPORT.md`、`docs/v107-startup-hotfix-20261006.md`、`docs/depths-encounter-variety-validation.md`。
